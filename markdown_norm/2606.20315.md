## A New Paradigm for Genomic Discovery

The Global Alliance for Genomics and Health (GA4GH) Beacon protocol is a standard for federated genomic data sharing. It allows researchers to query whether a specific genetic variant exists within a dataset without needing full access to individual-level sequences. However, traditional Beacon deployments are vulnerable to two major privacy risks. First, the host institution—the entity running the Beacon—can see exactly what a researcher is searching for and what the results are. This can reveal sensitive research interests or preliminary findings. Second, if a researcher can query the same dataset repeatedly, they might use the aggregate counts to infer whether a specific person is part of that dataset, a technique known as a membership-inference attack.

![bioeth-beacon-overview](https://paper-assets.alphaxiv.org/figures-normalized/figures/2606.20315v1/img-0.jpeg)
*{fig:bioeth-beacon-overview}: High-level overview of the bioETH-Beacon system, showing how contributors upload encrypted data and researchers receive encrypted results through a blockchain-based compute layer.*

The bioETH-Beacon project addresses these issues by moving the genomic discovery process onto a blockchain that supports Fully Homomorphic Encryption (FHE). Specifically, the system utilizes an FHE-enabled Ethereum Virtual Machine (fhEVM). This allows the entire query process—from the initial search for a variant to the final calculation of the result—to happen while the data remains encrypted. By doing so, even the entities maintaining the blockchain or hosting the data cannot see the contents of the queries or the results. This creates a "trustless" environment where privacy is guaranteed by mathematics rather than just institutional policy.

## Confidentiality Through Fully Homomorphic Encryption

At the heart of bioETH-Beacon is Fully Homomorphic Encryption (FHE). Unlike standard encryption, which requires data to be decrypted before it can be used in calculations, FHE allows computations to be performed directly on the encrypted data (ciphertexts). The result of such a calculation is also encrypted, and only someone with the correct decryption key can see the final answer.

In the context of a genomic Beacon, this means:
1.  **Encrypted Inputs:** Hospitals and biobanks encrypt their genomic counts before sending them to the blockchain.
2.  **Encrypted Processing:** The blockchain runs a "scan" over the data to match a researcher's query against the stored records, all while both the query and the records are encrypted.
3.  **Encrypted Results:** The final aggregate count is delivered to the researcher as an encrypted handle, which they can then decrypt using a separate Key Management Service (KMS).

By using the Zama fhEVM, bioETH-Beacon leverages a technology called TFHE (Torus FHE), which is particularly efficient for the kind of integer comparisons and additions needed for genomic counts. The system supports various encrypted data types, such as $\text{euint32}$, $\text{euint64}$, and up to $\text{euint256}$, ensuring that genomic data of various scales can be handled securely.

## System Architecture and Smart Contract Logic

The architecture of bioETH-Beacon is split into two distinct layers of smart contracts: a public registry and an encrypted compute layer. This separation ensures that sensitive genomic data is isolated from public metadata.

![system-architecture](https://paper-assets.alphaxiv.org/figures-normalized/figures/2606.20315v1/img-1.jpeg)
*{fig:system-architecture}: The dual-layer architecture consisting of the public BeaconRegistry for policy management and the ConfidentialBeacon family for encrypted data storage and computation.*

The `BeaconRegistry` contract handles administrative tasks. It stores dataset metadata, manages which hospitals are approved to contribute, and tracks rate limits for researchers. It does not store any encrypted genomic information. The actual work happens in the `ConfidentialBeacon` family of contracts. These contracts store the encrypted "marker-count" pairs. Each marker (a genomic variant) is converted into an opaque identifier, a $\text{markerId}$, using a hashing process to ensure it doesn't reveal information before encryption.

The query process follows a specific lifecycle. Because FHE operations are computationally expensive and the blockchain has limits on how much work can be done in a single transaction (measured in Homomorphic Computation Units, or HCU), queries are processed in "chunks." A researcher starts a query, and then one or more transactions are sent to process segments of the dataset.

![dataset-and-query-lifecycles](https://paper-assets.alphaxiv.org/figures-normalized/figures/2606.20315v1/img-2.jpeg)
*{fig:dataset-and-query-lifecycles}: State machine diagrams for the dataset lifecycle (from registration to retirement) and the query lifecycle (from creation to finalization).*

To maintain privacy, the scan kernel is "oblivious." It performs the same sequence of operations for every single entry in the dataset, regardless of whether a match is found. This prevents anyone from deducing information by looking at how long a query takes or which parts of the data were accessed.

## The Three-Tier Design Matrix

One of the unique contributions of this work is the definition of three execution tiers (T3, T4, and T5), allowing users to choose the right balance between privacy and computational cost.

*   **T3 (Reference Tier):** This tier offers maximum privacy. Both the marker IDs and the counts are fully encrypted. The search happens as a linear scan over all entries, and the cost scales as $\Theta(N)$, where $N$ is the number of entries uploaded.
*   **T4 (Optimization Tier):** This tier is functionally identical to T3 but uses smaller encrypted data types (like $\text{euint32}$ instead of $\text{euint64}$) for the internal accumulators. This reduces the HCU cost per operation, allowing more data to be processed in a single block.
*   **T5 (Slot Tier):** This tier represents a significant trade-off. It uses a fixed set of "slots" for specific markers. While the counts are still encrypted, the marker indices themselves are public. This allows for much faster queries, as the system can jump directly to the relevant slot, making the cost $\Theta(M)$, where $M$ is a fixed number of slots.

The system also includes specialized contracts for filtering. Researchers can query for counts within specific subgroups, such as sex, age bands, or phenotypes. The most advanced version, the Multi-filter (G1) contract, allows for complex queries that combine multiple filters (e.g., "how many males over 50 have this variant?") while keeping all intermediate results encrypted.

## Bounded Noise and Query Protection

To defend against membership-inference attacks, bioETH-Beacon introduces an optional mechanism for injecting "bounded noise" into the results. If a researcher can see exact counts, they might be able to tell if a specific individual was added to a dataset by watching the count increment by one.

By adding a random noise value $\nu$, the system obscures the true count $c$. The final result $\tilde{c}$ is calculated as:

$$\tilde{c} = c + \nu$$

The noise $\nu$ is sampled from a uniform distribution:

$$\nu \sim U\{0, \dots, B-1\}$$

In this equation, $B$ is a bound that determines the maximum amount of noise. Crucially, this noise generation happens entirely within the encrypted domain of the FHE coprocessor. This ensures that even the person coordinating the query cannot manipulate or observe the noise value to "undo" the privacy protection. While this is not a formal guarantee of differential privacy, it significantly increases the "cost" for an attacker to successfully probe the dataset.

## Performance Benchmarks and Practical Constraints

The researchers conducted extensive testing using synthetic genomic panels to understand how the system performs in practice. Because FHE is intensive, the main constraints are the HCU budget and the "sequential depth" limit—the number of dependent FHE operations allowed in one go.

Tests showed that for the T3 tier, the system scales linearly. For a dataset with $N = 1,500$ entries, a query required about 73.8 million EVM gas and several transactions to complete. The research identified that the safe "chunk size" for these transactions is approximately 29 entries for $\text{euint64}$ data, meaning larger datasets simply require more chunks.

![query-scaling-comparison](https://paper-assets.alphaxiv.org/figures-normalized/figures/2606.20315v1/img-7.jpeg)
*{fig:query-scaling-comparison}: Comparison of query gas costs across T3, T4, and T5 tiers. While T3 and T4 scale linearly with the number of entries $N$, T5 remains flat because it uses a fixed number of slots $M$.*

The evaluation also found a "crossover point" where different tiers become more economical. For example, in a panel with 1,000 potential markers, the T3 tier (full encryption) is cheaper if the dataset is very sparse ($N \approx 246$ entries). However, if the dataset is more dense ($N \approx 484$ entries), the T5 tier (slot-based) becomes more efficient despite its higher initial setup cost.

## Broader Impact on Genomic Data Sharing

The bioETH-Beacon project demonstrates that it is possible to build a genomic discovery tool that is both functional and highly private by leveraging blockchain and FHE. By removing the need to trust a central host with plaintext data, it addresses one of the primary barriers to data sharing in the biomedical community.

While the current prototype is a proof-of-concept, it provides a roadmap for future developments, such as using Zero-Knowledge Proofs (ZKP) to ensure that hospitals are uploading valid data without revealing it, or scaling the system to handle population-sized genomic catalogs. By providing a flexible, tier-based design, bioETH-Beacon allows different research consortia to choose the level of privacy and cost that best fits their specific needs, paving the way for more secure and collaborative genomic research.
