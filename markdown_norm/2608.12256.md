## Introduction to Hybrid Traffic Control

Urban traffic signal control is a complex task that requires balancing real-time responsiveness with long-term efficiency. Traditional methods often fall into two camps: Model Predictive Control (MPC), which uses mathematical models to predict future traffic and optimize signal plans under strict constraints, and Reinforcement Learning (RL), which learns control policies through trial and error in simulated environments. While MPC is transparent and guarantees that signal timings follow legal and safety requirements, it often struggles to adapt to unexpected traffic patterns that fall outside its predictive model. Conversely, RL is highly adaptive but often acts as a "black box," making decisions that can be difficult for traffic managers to verify or interpret.

![mpc-rl-interface](https://paper-assets.alphaxiv.org/figures-normalized/figures/2608.12256v1/figures/mpc-rl-interface.png)
*{fig:mpc-rl-interface}: Comparison of different integration patterns between MPC and RL. SelectLight introduces "post-optimization selection," where RL chooses from a set of feasible plans generated by MPC.*

The research presents SelectLight, a framework designed to merge these two paradigms by introducing a new integration pattern called "post-optimization selection." In this approach, a distributed MPC system first generates a diverse set of feasible, high-quality candidate signal plans for each intersection. Then, a multi-agent RL policy selects the most appropriate plan for the current and predicted situation. This structure ensures that every action taken by the system is a valid, pre-computed signal plan that satisfies all operational constraints, while the selection process remains adaptive and capable of learning from actual network outcomes.

## The Post-Optimization Selection Paradigm

Most existing hybrid systems use RL to either configure the parameters of an MPC problem (pre-optimization configuration) or to adjust the output of an MPC solver (post-optimization correction). SelectLight differs by treating the MPC solver as a generator of possibilities. By using a multi-objective optimization approach, the MPC solver produces several "Pareto-optimal" plans—plans that represent different trade-offs between objectives like minimizing delay, reducing queue lengths, or minimizing vehicle stops.

The selection of a single plan from this set is traditionally done using fixed, hand-tuned rules. However, fixed rules cannot account for the complex, closed-loop interactions of a dynamic traffic network. By using a learned selector, SelectLight can adapt its preferences based on experience. For instance, it might learn that in certain congested states, prioritizing the clearing of a specific queue is more beneficial for the overall network than minimizing total average delay. This paradigm allows the system to remain grounded in the physical reality of the traffic network (via MPC) while gaining the strategic flexibility of a learning agent.

## Hierarchical Control Architecture

SelectLight operates as a hierarchical system that functions in a receding horizon manner. The control process is divided into two distinct levels that update every macro-step $t$, which typically represents an interval of 5 seconds.

![selectlight-framework](https://paper-assets.alphaxiv.org/figures-normalized/figures/2608.12256v1/figures/framework.png)
*{fig:selectlight-framework}: The SelectLight hierarchical architecture, showing the interaction between the cloud-based prediction module, the per-intersection candidate generators, and the selectors.*

The workflow follows these steps:
1.  **Prediction:** A cloud-based module uses Automatic Vehicle Identification (AVI) data to predict vehicle arrivals at each intersection. It corrects prediction errors in real-time by comparing expected arrivals with actual detections.
2.  **Generation:** At each intersection $i$, a candidate generator solves a local multi-objective optimization problem. It considers a prediction horizon $H$ (e.g., 120 seconds) and produces a set $K$ of candidate signal plans.
3.  **Selection:** A shared RL policy (the "selector") evaluates the local traffic state $o_{i,t}$ and the features of the candidate plans. It then picks one plan to be executed.
4.  **Execution:** Only the first $M$ seconds of the selected plan are executed before the entire process repeats, allowing the system to constantly adjust to new data.

## Candidate Generation via Multi-Objective MPC

The lower level of SelectLight focuses on generating a set of high-quality, feasible signal plans. This is achieved through a State-Pruned Multi-Objective Dynamic Programming (SP-MODP) algorithm.

### Traffic Modeling and Objectives
To evaluate potential signal plans, the system uses a Newellian Point-Spatial Queue model. This model tracks two types of queues: the point queue $Q^p$, which represents the number of stopped vehicles, and the spatial queue $Q^s$, which tracks the physical length of the queue back from the intersection. The state of the point queue at time $k$ is updated recursively:

$$Q^p(k) = Q^p(k-1) + \hat{q}^{\text{arr}}(k) - \hat{q}^{\text{dep}}(k)$$

where $\hat{q}^{\text{arr}}(k)$ and $\hat{q}^{\text{dep}}(k)$ are the predicted arrivals and departures, respectively.

![queue-model](https://paper-assets.alphaxiv.org/figures-normalized/figures/2608.12256v1/figures/newellian-queue-model.png)
*{fig:queue-model}: The Newellian queue model used for evaluating candidate plans, tracking both the number of vehicles and the physical extent of congestion.*

The generator evaluates each candidate plan based on three key objectives:
*   **Total Queueing Delay ($J_{\text{delay}}$):** The cumulative time vehicles spend waiting in queues.
*   **Peak Queue Accumulation ($J_{\text{queue}}$):** The maximum spatial queue length, which helps prevent spillback into upstream intersections.
*   **Total Stops ($J_{\text{stop}}$):** The number of times vehicles are forced to stop, which relates to fuel consumption and emissions.

### The SP-MODP Solver
The SP-MODP solver explores the decision space by building a lattice of possible signal phase transitions over the horizon $H$. To keep the computation efficient, the algorithm uses "pruning." It discards any partial plan that is clearly inferior to another (i.e., dominated in all three objectives). It also applies a label cap $K_{pf}$ to limit the number of candidates kept at each step. This ensures that the solver can run in real-time, even for complex intersections.

## Adaptive Selection via Attention-Based Learning

The upper level uses Multi-Agent Reinforcement Learning (MARL) to choose the final plan. The goal is to maximize the long-term efficiency of the network, which is defined by a reward function $r_{i,t} = -D_{i,t}$, where $D_{i,t}$ is the realized local queueing delay.

### Topology-Aware Encoding
Intersections vary in their geometry—some have four arms, some have three, and some have complex turn lanes. To handle this heterogeneity, SelectLight uses a topology-aware encoder. It represents the intersection as a graph $G_{lp,i}$ where lanes are connected to the signal phases that serve them. An attention mechanism aggregates features from individual lanes into phase embeddings, and then into a single intersection embedding.

![intersection-encoder](https://paper-assets.alphaxiv.org/figures-normalized/figures/2608.12256v1/figures/intersection-encoder.png)
*{fig:intersection-encoder}: The attention-based encoder architecture that allows the policy to understand the physical structure of different intersections.*

### Candidate Selection Policy
The selector compares the intersection embedding with the features of each candidate plan generated by the MPC level. These features include the predicted objective scores ($J_{\text{delay}}$, $J_{\text{queue}}$, $J_{\text{stop}}$) and the structure of the signal timings. By using masked scaled dot-product attention, the selector can handle a variable number of candidates. It learns to recognize which plan "fits" the current traffic context best. For example, it might learn to select a plan with a slightly higher predicted delay if that plan significantly reduces the peak queue on a critical bottleneck link.

## Empirical Evaluation and Robustness

The SelectLight framework was tested on two realistic urban networks (Lianyungang and Jiading) using the SUMO traffic simulator. The results showed that SelectLight consistently outperformed traditional methods like Max Pressure control and standalone RL policies.

### Performance Under High Demand
One of the most significant findings was the system's robustness under heavy traffic. As demand increased from a baseline level of $1.0$ to a congested level of $2.0$, the performance gap between SelectLight and other methods widened. While standard RL policies often struggled to maintain stability under extreme congestion, SelectLight's reliance on constrained MPC plans ensured that it always operated within safe and reasonable limits, leading to much lower average waiting times and higher throughput.

### Zero-Shot Transferability
A common problem with RL is that a policy trained on one city or one demand level might fail when moved to another. SelectLight demonstrated strong "zero-shot" transferability. Because the candidate plans are generated online based on the specific geometry and current arrivals at an intersection, the RL selector only needs to learn the general strategy of how to pick between trade-offs. This allowed a policy trained on one network to perform effectively on a completely different network without any additional training.

## Significance and Practical Implications

SelectLight addresses several critical barriers to the adoption of advanced traffic control in the real world. 

1.  **Safety and Constraints:** By selecting from a set of MPC-generated plans, the system guarantees that all timing constraints (like minimum green times and yellow intervals) are always met. Traffic engineers can trust that the system will never produce an "impossible" signal sequence.
2.  **Transparency:** The framework is not a "black box." For any given decision, a human operator can see exactly what the alternatives were and what the predicted trade-offs (delay vs. stops vs. queues) looked like for each candidate.
3.  **Real-Time Efficiency:** Despite the complexity of solving multi-objective optimization problems, the SP-MODP algorithm is highly efficient. In tests, it generated plans in less than 6 milliseconds per intersection, which is well within the 5-second decision window required for real-time control.
4.  **Multi-Objective Balancing:** The system avoids the need for engineers to manually weight different objectives (e.g., deciding if one stop is worth three seconds of delay). Instead, the RL policy learns the optimal balance by observing how different choices impact the actual realized traffic flow over time.

By combining the mathematical rigor of MPC with the adaptive intelligence of MARL, SelectLight provides a scalable and robust solution for managing the increasing complexity of modern urban traffic networks.
