## Introduction to Autonomous GUI Agents and Safety

The integration of Large Language Models (LLMs) into Graphical User Interface (GUI) environments has enabled the creation of autonomous agents capable of performing complex tasks across mobile and web applications. These agents can manage schedules, process online orders, and navigate intricate workflows that previously required manual human intervention. However, as these agents gain more autonomy, they encounter significant challenges regarding user privacy and operational safety.

In real-world deployment, an agent may encounter screens containing highly sensitive information, such as bank account details, private messages, or personal identification. Current state-of-the-art models often prioritize task completion over safety, leading to potential privacy infringements or irreversible actions like deleting critical files or executing unauthorized financial transactions. To mitigate these risks, there is a critical need for agents to recognize "user-sensitive" states—junctures in a task where human judgment or confirmation is required before proceeding.

The research presented here focuses on developing a systematic exploration method to discover these sensitive states within a GUI application. By focusing on identifying queries and interaction paths that lead to private or high-stakes environments, engineers can curate datasets that train agents to signal for a "user handover" rather than acting autonomously in risky scenarios.

## The Explorer Agent Architecture

The framework utilizes a dual-model approach to balance task execution with exploration. This architecture separates the logic of "how to act" from the logic of "where to explore."

1.  **Native Language Model (Native LM):** This model acts as the primary driver for GUI interactions. It is responsible for selecting specific actions—such as clicks, scrolls, or text inputs—based on the current screen state. In this work, the M3A agent is used as the native model to execute the interaction steps.
2.  **Explorer Language Model (Explorer LM):** This is the core component that directs the discovery of user-sensitive scenarios. Instead of focusing on task completion, the Explorer LM is trained with a pure exploration objective. Its goal is to generate novel queries that push the boundaries of the agent's known environment, specifically targeting interaction paths that lead to sensitive or "critic" screens.

![workflow-diagram](https://paper-assets.alphaxiv.org/figures-normalized/figures/2606.25705v1/dial_final.png)

The Explorer LM maintains a policy $\Pi_\theta(s_0)$, where $\theta$ represents the model parameters and $s_0$ represents the application's home screen. Through iterative training, this policy learns to propose queries that maximize the likelihood of discovering unseen or sensitive UI states.

## Systematic Exploration: Selection and Saturation

A major challenge in GUI exploration is avoiding "structureless wandering," where an agent repeats similar actions without discovering new functionality. This framework introduces two key algorithms to ensure diverse and efficient exploration of the query space.

### Query Selection and Expansion
The exploration begins by generating $N \times M$ episodes, consisting of $N$ batches of $M$ queries. To prevent the model from over-focusing on a single area of the application, the framework employs a selection mechanism. Starting from a user-provided base trajectory $T_0$ and a general instruction $I$, new queries $u_i$ are generated. 

Each new query is converted into a vector embedding, and its cosine similarity is measured against existing queries in the current batch and the historical memory bank. A query is only retained if its similarity to previous entries is below a threshold $\tau = 0.85$. This ensures that every selected query represents a distinct task or interaction path, effectively expanding the agent's "knowledge frontier" of the application.

### The Saturation Mechanism
Infinite exploration is computationally expensive. To optimize resources, the framework uses a saturation algorithm to determine when the agent has likely discovered most unique interactions for a given state. By monitoring the number of unique queries generated per batch, the system fits mathematical functions (linear and polynomial) to the data to identify an "inflection point." When the rate of discovery for new, unique queries drops significantly, the system declares the current phase "saturated" and moves to the training phase.

## Reward Modeling and Reinforcement Learning

The heart of the explorer agent's intelligence lies in its reward function, which is designed to prioritize novelty and sensitivity. The training process uses Group Relative Policy Optimization (GRPO), a reinforcement learning technique that compares the rewards of a group of generated outputs to update the model policy.

The total reward for a query $u_i$ and its associated steps $a_{ij}$ is defined as:

$$R(u_i, a_{ij}) := (\text{QueryNovelty}(u_i)) \times [\text{StepNovelty}(a_{ij}) + \text{CategoryNovelty}(a_{ij})]$$

### Novelty Components
*   **Query Novelty:** The framework clusters queries in the memory bank using k-means. Queries that fall into smaller, less populated clusters are given higher rewards. This is calculated using $\exp\{-\text{len}(\text{queries}[j])\}$, where the length refers to the number of queries in cluster $j$.
*   **Step Novelty:** This measures how different the individual actions (like clicking a specific button) are from previously executed actions. It uses cosine similarity of text descriptions of the actions to reward the agent for finding new paths through the UI.
*   **Category Novelty:** This is the most critical component for safety. The system categorizes screens as "critic" (sensitive) or "not critic." If a sequence of actions leads to a "critic" screen that has been rarely visited, the agent receives a significantly higher reward.

Before the RL phase, the model undergoes Supervised Fine-Tuning (SFT) to ensure it can accurately predict the sequence of actions required for a given query. This ensures that the exploration is logical and that the agent can actually reach the states it intends to explore.

## Experimental Findings and Convergence

The methodology was tested over three distinct training rounds. The results demonstrate that the explorer agent effectively "maps" the sensitive regions of the GUI application.

### Shrinking Exploration Space
As the agent progresses through training rounds, the total available reward decreases by several orders of magnitude, from $10^{-2}$ to $10^{-5}$. This reduction indicates that the agent is successfully saturating the discoverable space—there are fewer "new" things to find because the explorer has already identified the majority of novel and sensitive states.

### Discovery of Non-Sensitive States
Over time, the frequency of "not-critic" (non-sensitive) screens increases in the roll-outs. This happens because the explorer agent has already exhausted most of the high-reward sensitive paths, eventually spending more time in mundane areas of the application. This shift is a positive indicator that the agent has thoroughly explored the sensitive boundaries and is now encountering the general background of the UI.

## Significance for Future AI Development

The primary contribution of this work is the shift from "task-oriented" exploration to "sensitivity-oriented" exploration. While traditional GUI agents are evaluated on how quickly they can complete a purchase or send a message, the explorer agent is evaluated on its ability to find the exact moments where an autonomous system *should stop*.

This research provides several benefits for the broader field of AI safety:
1.  **Safety-First Data Curation:** Engineers can use this explorer agent to automatically generate thousands of edge cases where user privacy is at risk, creating a "safety dataset" for training more reliable models.
2.  **User-in-the-Loop Integration:** By identifying sensitive states, developers can implement hard-coded "handover" triggers. For example, if an agent recognizes it is on a "critic" screen associated with financial transactions, it can pause and prompt the user: "I have reached a sensitive payment screen. Please complete this step manually."
3.  **Reliable Deployment:** Systematic exploration reduces the "surprise factor" when deploying agents in the wild. Knowing the sensitive boundaries of an application allows for more predictable and trustworthy AI behavior.

By iteratively refining the model using GRPO and novelty-based rewards with a fixed learning rate of $5 \times 10^{-7}$, the framework demonstrates a robust path toward building agents that are not just capable, but also aware of the ethical and privacy-related boundaries of the environments they inhabit.
